# 01 — Token Propagation and Service-to-Service

## 1. Two identities

A distributed request may represent:

```text
end_user = user-123
calling_service = orders-service
```

Keep these identities separate in authorization and audit events.

## 2. Propagation

Simple approach:

```text
Gateway -> Service A -> Service B
          same user token
```

This can be easy but may give every downstream service more authority than it needs.

## 3. Exchange / delegation

A more isolated model can be:

```text
incoming credential
       ↓
token exchange / delegation
       ↓
service-specific credential
```

The resulting token can use:

```text
narrow audience
narrow scope
shorter lifetime
```

## 4. Service credentials

For machine-to-machine calls, use a suitable service authorization model such as Client Credentials when appropriate.

## 5. Header trust

Never trust external user-controlled headers such as:

```text
X-User-Id
X-Admin
X-Tenant-Id
```

unless a protected upstream trust boundary guarantees they were generated by an authenticated internal component.

## 6. Lab

Build:

```text
gateway -> orders -> inventory
```

and test wrong audience, missing scope, expired credential, and forged identity headers.
